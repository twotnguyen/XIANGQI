**Việc cần làm:**
1. `POST /api/v1/auth/reset-password` body strict `{ newPassword, operationId }`, chỉ chấp nhận **recovery session** (JWT có `amr` chứa `recovery`/phiên tạo từ luồng recovery, dùng một lần). Phiên đăng nhập thường ⇒ 403.
   ```
   ① Transaction: fence mọi app_sessions của user (revoked_at) + INSERT auth_security_jobs (PASSWORD_CHANGED, ALL, snapshot)
   ② Gọi Auth Admin updateUserById(password) — ngoài transaction
   ③ Thành công ⇒ { status:'COMPLETED' }; lỗi ⇒ giữ fence, { status:'PENDING' }, retry cùng operationId (idempotent)
   ```
   Mật khẩu 10–128; không log/lưu mật khẩu. Recovery session không được dùng cho route sản phẩm (guard từ chối).
2. Trigger DB ở TK05.2.2 đã bao phủ trường hợp client gọi thẳng Auth `updateUser` — viết test chứng minh.
3. `POST /api/v1/auth/complete-profile` body strict `{ username, displayName? }`:
   ```sql
   BEGIN;
   SELECT username FROM profiles WHERE user_id = $1 FOR UPDATE;
   -- đã có username ⇒ ROLLBACK, 409 CONFLICT "Tên đăng nhập đã được chọn, không thể đổi"
   UPDATE profiles SET username = lower($2), display_name = coalesce($3, lower($2)), profile_verified_at = now() WHERE user_id = $1;
   -- 23505 ⇒ 409 "Tên đăng nhập đã được sử dụng"
   COMMIT;
   ```
   Username sai định dạng ⇒ 400 `VALIDATION_ERROR`. Đích đã nhớ không được tiêu thụ ở đây (join là bước riêng).
4. Test `tests/integration/issue-052.test.ts`, `issue-054.test.ts` (hai người cùng chọn `alice` bằng barrier; cùng người gọi 2 lần song song).

**Bẫy dễ gặp:** không khoá hàng ⇒ ghi username 2 lần; dựa vào client tự logout sau khi đổi mật khẩu.
