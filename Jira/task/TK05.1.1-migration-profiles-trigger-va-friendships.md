**Việc cần làm:**
1. `supabase/migrations/<ts>_profiles.sql` — bảng `public.profiles`:
   | Cột | Kiểu | Ràng buộc |
   |---|---|---|
   | `user_id` | uuid | PK, FK → `auth.users(id)` `ON DELETE RESTRICT` |
   | `username` | text | UNIQUE, cho phép NULL (tài khoản Google chưa chọn) |
   | `display_name` | text | NOT NULL |
   | `profile_verified_at` | timestamptz | NULL = hồ sơ tạm chưa chứng minh sở hữu email; **chỉ server ghi** |
   | `created_at` | timestamptz | NOT NULL DEFAULT now() |
   ```sql
   CHECK (username IS NULL OR username ~ '^[a-z0-9_]{3,24}$')
   CHECK (char_length(display_name) BETWEEN 1 AND 40)
   ```
2. Trigger `AFTER INSERT ON auth.users` (`SECURITY DEFINER`, `SET search_path = ''`, tên bảng viết đầy đủ `public.profiles`): đọc `raw_user_meta_data->>'signup_username'` và `signup_display_name` (display_name mặc định = username; Google không có username ⇒ NULL, display_name lấy tên Google hoặc phần trước @ email, cắt 40 ký tự). **Không** đọc quyền/vai trò hay `profile_verified_at` từ metadata. Đổi metadata về sau **không** cập nhật profiles.
3. `supabase/migrations/<ts>_friendships.sql` — `public.friendships(id uuid PK, user_a uuid FK profiles, user_b uuid FK profiles, requested_by uuid FK profiles, status text, created_at)`:
   ```sql
   CHECK (user_a < user_b)                    -- luôn sắp xếp id: nhỏ ở user_a
   CHECK (user_a <> user_b)
   CHECK (requested_by IN (user_a, user_b))
   CHECK (status IN ('PENDING','ACCEPTED'))
   UNIQUE (user_a, user_b)                    -- một cặp = một hàng
   ```
   Index `(user_a, status)`, `(user_b, status)`. FK `ON DELETE RESTRICT`.
4. Test tích hợp `tests/integration/issue-035.test.ts`, `issue-036.test.ts` — đủ các ca ở TK05.1.1.

**Bẫy dễ gặp:** chỉ chuẩn hoá chữ thường ở giao diện ⇒ gọi API trực tiếp tạo được `Alice` và `alice`. Thiếu `CHECK (user_a < user_b)` ⇒ một cặp có 2 hàng, 2 lời mời.
