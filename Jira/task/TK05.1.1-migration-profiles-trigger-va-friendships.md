## 1. MỤC TIÊU (đọc trong 1 phút)

Tạo 2 bảng đầu tiên bằng **migration `.sql`**:
- **`profiles`** — hồ sơ người dùng (username, tên hiển thị), tự tạo bằng **trigger** mỗi khi Supabase Auth có user mới.
- **`friendships`** — quan hệ bạn bè; **một cặp người chỉ có một dòng** dù ai gửi lời mời trước.

Ràng buộc đặt **ở tầng DB** để dù code có lỗi, dữ liệu sai vẫn **không thể** được ghi.

## 2. KHÁI NIỆM CẦN BIẾT

| Khái niệm | Giải thích |
|---|---|
| **Migration** | File `.sql` mô tả thay đổi schema, áp bằng `pnpm db:reset` — xem [Từ điển](../05-TU-DIEN-KY-THUAT.md#migration). ⛔ **Không** `prisma migrate` |
| **`auth.users`** | Bảng user do Supabase Auth quản lý (email, mật khẩu). Ta **không** sửa bảng này; `profiles` trỏ tới nó |
| **Trigger `SECURITY DEFINER`** | Hàm chạy với quyền của người tạo hàm (để ghi vào `public.profiles` khi Auth thêm user). Bắt buộc `SET search_path = ''` và viết tên bảng đầy đủ để tránh bị lừa gọi nhầm bảng |
| **`raw_user_meta_data`** | Dữ liệu phụ gửi lúc đăng ký (username, tên hiển thị). **Người dùng tự sửa được** ⇒ chỉ đọc lúc tạo, **không** tin cho quyền/vai trò |
| **`CHECK (user_a < user_b)`** | Luôn lưu id nhỏ hơn ở `user_a` ⇒ A→B và B→A thành **cùng** một dòng |

Luật nghiệp vụ: username 3–24 ký tự `a-z 0-9 _`, lưu chữ thường (`BR-AUTH-01/02`); tên hiển thị 1–40 ký tự (`BR-AUTH-04`).

## 5. HƯỚNG DẪN LÀM TỪNG BƯỚC

### 5.1 Tạo file migration
```bash
supabase migration new profiles       # tạo supabase/migrations/<timestamp>_profiles.sql
```

### 5.2 Bảng `public.profiles`

| Cột | Kiểu | Ràng buộc |
|---|---|---|
| `user_id` | uuid | PK, FK → `auth.users(id)` `ON DELETE RESTRICT` |
| `username` | text | UNIQUE, **cho phép NULL** (tài khoản Google chưa chọn username) |
| `display_name` | text | NOT NULL |
| `profile_verified_at` | timestamptz | NULL = chưa chứng minh sở hữu email; **chỉ server ghi** |
| `created_at` | timestamptz | NOT NULL DEFAULT now() |

```sql
CHECK (username IS NULL OR username ~ '^[a-z0-9_]{3,24}$')
CHECK (char_length(display_name) BETWEEN 1 AND 40)
```

### 5.3 Trigger tạo profile
`AFTER INSERT ON auth.users`, hàm `SECURITY DEFINER`, `SET search_path = ''`, viết `public.profiles` đầy đủ:
- `username` = `lower(raw_user_meta_data->>'signup_username')` (Google không có ⇒ NULL).
- `display_name` = `signup_display_name` → nếu thiếu: username → tên Google (`full_name`) → phần trước `@` của email; cắt 40 ký tự.
- **Không** đọc `profile_verified_at`, quyền, vai trò từ metadata.
- Chỉ chạy lúc **tạo**; sửa metadata về sau **không** cập nhật `profiles`.

### 5.4 Bảng `public.friendships`
```sql
CREATE TABLE public.friendships (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_a uuid NOT NULL REFERENCES public.profiles(user_id) ON DELETE RESTRICT,
  user_b uuid NOT NULL REFERENCES public.profiles(user_id) ON DELETE RESTRICT,
  requested_by uuid NOT NULL REFERENCES public.profiles(user_id) ON DELETE RESTRICT,
  status text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  CHECK (user_a < user_b),                    -- id nhỏ luôn ở user_a
  CHECK (requested_by IN (user_a, user_b)),
  CHECK (status IN ('PENDING','ACCEPTED')),
  UNIQUE (user_a, user_b)                     -- một cặp = một dòng
);
CREATE INDEX ON public.friendships (user_a, status);
CREATE INDEX ON public.friendships (user_b, status);
```
(`user_a < user_b` đã bao gồm `user_a <> user_b`.)

### 5.5 Test (viết TRƯỚC) — `issue-035.test.ts`, `issue-036.test.ts`
Mỗi ca ở phần kiểm thử (QA05.1.1-01..13) có 1 test tương ứng, kiểm **mã SQLSTATE** (`23514`, `23505`, `23503`) chứ không chỉ "có lỗi". Tạo user Auth bằng Admin API thật (không INSERT thẳng `auth.users`).

**Thử phá:** bỏ `CHECK (user_a < user_b)` ⇒ test "một cặp một dòng" phải đỏ.
